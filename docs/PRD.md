# PRD · 对话式数据分析 Agent

| | |
|---|---|
| 版本 | v1.0 |
| 定位 | 面向中小工厂 / 电商商家的自然语言数据分析助手（单机私有化部署） |
| 不做什么 | 不做 BI 报表平台、不做数据仓库、不做多租户 SaaS |

## 1. 问题

小商家有数据，但没有分析师：

- 数据散在 Excel、门店系统导出的 CSV、一个 MySQL 里；
- 想问的问题都很具体（"上个月哪个渠道亏了""哪个产品卖得最好"），但**不会写 SQL**；
- 招一个数据分析师不划算，买 BI 工具又要人先建模型。

所以产品的核心价值只有一句话：**把一句中文问题，变成"可信的 SQL + 能看的图 + 说人话的结论"，
并且让用户知道结论是从哪几行数据来的。**

## 2. 用户与角色

| 角色 | 典型人 | 能做什么 |
|---|---|---|
| `admin` | 老板 / IT | 全部；管人、管数据源、看审计 |
| `analyst` | 运营 / 店长 | 接数据源、提问、出报告、设定时分析 |
| `viewer` | 店员 / 外部顾问 | 只能看和提问；**不能改数据源、不能执行写 SQL** |

## 3. 关键需求（带验收口径）

### R1 数据接入
- 支持上传 Excel / CSV，支持连接 SQLite / MySQL / PostgreSQL。
- 上传后必须给出**清洗报告**：读入行数、写入行数、丢弃空行数、丢弃重复行数、逐条清洗说明。
- 防护：扩展名白名单、大小上限（默认 20MB，流式读取、超限立刻中断）、落盘文件名用 UUID
  （用户文件名不参与路径）、SQLite 路径必须存在。
- 验收：上传一份含"空行 + 重复行 + 前导零编码 + 首尾空格"的 CSV，报告里这四类问题都要被点名。

### R2 数据理解（schema / profiling）
- 自动产出：表/列、类型、行数、低基数列的 `sample_values`、表间关系推断（`relations` / `column_lookup`）。
- 数据质量画像：每列缺失率、唯一性、TOP 值；标记疑似 PII（手机/邮箱/身份证/地址/姓名）。
- 验收：样例数据里 `订单明细` 的 `城市` 列应带 4 个取值，`产品` 表应被识别为维度表。

### R3 问答
- 8 节点链路：理解 →（澄清）→ 生成 SQL →（确认/拒绝）→ 执行 → 分析 →（诊断）→ 可视化 → 回答。
- 模糊问题必须**反问澄清**，不允许猜。
- 0 行结果必须**明确说没有数据**，不允许编造结论。
- 部分数据源失败要继续出结果，并明确告警"本次结果不含 X 源"。
- 验收见 §5 场景 A/B。

### R4 安全
- SQL 只读：写操作、DDL、多语句、超长、危险函数一律拒绝（详见 `architecture.md §3.2`）。
- 默认自动补 `LIMIT 1000`；结果行数/单元格数有上限；结果被截断要告知用户。
- 每个请求有 `request_id`，统一错误体返回它。

### R5 权限
- JWT（access 30 分钟）+ refresh token（7 天，刷新即轮换，旧 token 立即失效）。
- viewer：`POST /api/datasources` → 403，`DELETE /api/datasources/{id}` → 403，
  `POST /api/auth/users` → 403；但 `GET /api/datasources` 和提问 → 200。

### R6 报告
- 从会话一键生成报告，**落库**（可按 id 反复下载），支持 markdown / html / pdf。
- 报告必须包含：原始问题、分析结论、原因诊断、优化建议、SQL、数据表格（前 20 行）。

### R7 定时分析
- 按固定间隔（≥5 分钟）自动跑一遍指定问题并出报告。
- 幂等：同一计划同一时刻只执行一次（重启 / 多副本都不重复）。
- 失败隔离：单个计划失败不影响其它计划；连续失败 3 次自动停用。

### R8 运维
- `/healthz`（存活）、`/readyz`（就绪：元数据库 + 关键表 + 任务服务）、`/metrics`（Prometheus）。
- 结构化 JSON 日志，每条带 `request_id`；审计事件落 `operation_logs`。
- 一键启动：`docker compose up -d --build --wait`；不填任何 Key 也能跑通（`LLM_PROVIDER=mock`）。

## 4. 非功能指标

| 指标 | 目标 | 实测 |
|---|---|---|
| NL2SQL 正确率（309 条归档用例） | ≥ 95% | **100%**（5 套数据，含 2 套未参与调参的留出集） |
| SQL 可执行率 | ≥ 99% | 100% |
| 平均生成延迟 | ≤ 3s | 1.5–2.1s（DeepSeek，temperature=0） |
| 上下文压缩后事实留存 | ≥ 90% | 100%（混合压缩） |
| 后端测试 | 全绿 | 273 passed |
| 覆盖率 | ≥ 70% | 74% |
| 恶意 SQL 拦截 | 100% | 7/7 攻击样本全部拒绝 |

## 5. 验收场景（可照着做）

### 场景 A：新用户第一次用（5 分钟）
1. `docker compose up -d --build --wait`，打开 `http://localhost:8080`。
2. 用 `admin / admin12345` 登录。
3. 数据源页看到系统预置的"示例·门店经营数据"（4 城市 × 3 渠道 × 5 产品，1200 行）。
4. 回对话页问："**2026年**各城市的销售额排名" → 看到 SQL、柱状图、结论。`n   > 注意：**不带时间范围**时（如"各城市的销售额排名"）Agent 会先反问时间段，`n   > 这是 PRD 里"指标/时间/粒度缺一即澄清"的设计，不是 bug。
5. 问："哪个渠道的利润最低，为什么" → 看到诊断原因 + 建议 + 图表。
6. 问："帮我看看销售情况" → **Agent 反问**要哪个指标，并给出 3 个可点选项。

### 场景 B：用户自己的脏数据
1. 数据源页上传 `data/samples/门店经营明细_待清洗.csv`。
2. 界面显示清洗报告：丢弃 1 行全空、1 行完全重复、`门店编号` 因前导零保持文本。
3. 数据质量画像里出现"门店编号 唯一"、"城市 缺失率"等风险提示。
4. 再上传同一文件（勾选增量）→ 写入 0 行（幂等）。

### 场景 C：只读用户
1. admin 在用户管理里建一个 `viewer`。
2. viewer 登录：能看数据源、能提问、能出报告。
3. viewer 点"新建数据源"/"删除"→ 按钮置灰或返回 403。

### 场景 D：恶意输入
在管理员账号下（或用 `curl`）提交下面几条，都应被拒绝并给出中文原因：

| 输入 | 期望 |
|---|---|
| `SELECT 1; DROP TABLE "订单明细"` | 只允许执行单条 SQL |
| `DROP TABLE "订单明细"` | 只允许只读查询 |
| `SELECT load_file('/etc/passwd')` | 禁止读取服务器文件 |
| `SELECT 1 , 1 , 1 ...`（>8000 字符） | SQL 过长 |
| `PRAGMA table_info('订单明细')` | 只允许只读查询 |

## 6. 成功标准（作品集视角）

- 面试官能在 **10 分钟内**：起服务 → 登录 → 问 3 个问题 → 看到 SQL/图/结论 → 导出报告。
- 代码层面能答出三个"为什么"：为什么 SQL 闸在执行侧、为什么用唯一约束做幂等、
  为什么 `mock` LLM 是正式组件。
- 每个数字都有出处：`docs/audit.md`（审计）、`backend/bench/README.md`（评测）、
  `docs/demo.md`（验收记录）。
